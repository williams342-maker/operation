# Agent machine access review

## Root cause and route inventory

`/install.sh` is `apps/web/public/install.sh`. Vite copies it into the web image and
`deploy/nginx/web.conf` serves it. The outer edge sends `/` to web and `/api/` to API.

The observed 502 was generated by origin nginx, not Cloudflare Access or the
application. At the matching UTC times nginx recorded an upstream connection reset and
connection refused for `127.0.0.1:18080`, coinciding with a Compose recreation and host
reboot. Successful installer responses were recorded before and after the interruption.

The agent calls `POST /api/agent/enroll`, `POST /api/agent/poll`, and `POST
/api/agent/tasks/ack`. Previously, neither enrollment nor later signed requests sent
Cloudflare Access service-token headers.

## Proposed architecture

Keep the dashboard Access policy unchanged. Add a narrowly scoped machine policy for
only `/install.sh` and the three exact agent endpoints. Permit a dedicated Access service
token; do not add a public bypass. Keep the application one-time enrollment token for
enrollment and the agent HMAC signature for later calls.

The installer stores machine credentials in
`/etc/opsworkbench-agent/machine-auth.env`, root-owned mode `0600`. systemd reads that
file without embedding values in the unit. The client sends the headers for enrollment,
poll, and acknowledgement. Errors contain only HTTP status, never bodies or credentials.

As a follow-up, publish a signed immutable agent artifact and verify its signature or
digest. This patch at least replaces the mutable branch archive with a commit-pinned
archive.

## Owner actions before deployment

1. Create or select a Cloudflare Access service token without copying it into source,
   CI output, tickets, or chat.
2. Add the four-path machine policy and verify policy precedence leaves the interactive
   dashboard policy intact.
3. Review and merge this patch, build immutable images, and use the existing staged
   deployment and rollback controls.

## Installation after approval and deployment

Connect from an administrator workstation:

```sh
ssh root@<managed-host>
```

Generate a fresh, one-use enrollment in OpsWorkbench and copy its newly generated
workflow. Paste it into the root session. The workflow uses hidden prompts, protected
temporary files and a curl config, checks HTTP status/content type/shebang/shell syntax,
displays the installer, and asks for confirmation. Do not use a workflow generated
before this patch and do not run `curl | bash`.

Validate without printing configuration contents:

```sh
systemctl is-enabled opsworkbench-agent.service
systemctl is-active opsworkbench-agent.service
stat -c '%U:%G %a %n' /etc/opsworkbench-agent /etc/opsworkbench-agent/*.env /etc/opsworkbench-agent/agent.json
systemctl restart opsworkbench-agent.service
systemctl is-active --quiet opsworkbench-agent.service
```

Expected modes are `0750` for the directory and `0600` for credential/config files.
After a controlled reboot, the enabled service must reconnect without an enrollment
token.

## Rollback

Redeploy the previously approved application image digest using the existing deployment
mechanism. To roll the agent source back on the enrolled host:

```sh
systemctl stop opsworkbench-agent.service
test -d /opt/opsworkbench-agent/source.previous
mv /opt/opsworkbench-agent/source /opt/opsworkbench-agent/source.failed
mv /opt/opsworkbench-agent/source.previous /opt/opsworkbench-agent/source
systemctl start opsworkbench-agent.service
```

If the machine policy is rolled back, revoke its service token and restore the prior
machine policy. Never delete or relax the interactive dashboard policy.
